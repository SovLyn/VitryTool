# 前后端接口契约规范

本规范定义前后端接口的**规划仪式**与**文档格式**。核心原则：**接口先行，契约为准，禁止只改代码不改文档**。

## 1. 接口规划仪式（每次探讨的前置步骤）

任何新功能或接口变更，在动手写代码之前必须完成：

1. 在 `docs/api/<feature>.md` 建立/更新契约文档（使用 [TEMPLATE.md](TEMPLATE.md)）。
2. 明确：命令列表、请求/响应类型、错误码、破坏性影响。
3. 契约文档经确认后，才允许进入后端实现与前端对接。

「探讨接口」≠「探讨代码」：接口确定后，后端与前端可以在各自目录中并行开发。

## 2. 命令命名

- 后端命令名：小驼峰（如 `getPeers`），与前端 `invoke` 调用的字符串一致。
- 一个功能的所有命令集中注册到 `lib.rs` 的 `invoke_handler`，按功能分组注释。

## 3. 数据约定

- 所有请求/响应类型必须是 `serde` 可序列化结构（后端）与对应 TS 接口（前端），字段命名统一小驼峰。
- 时间统一为 ISO 8601 字符串；无歧义的单位必须写明（如 `timeout_ms`）。
- 可选字段显式标注；不存在的字段前端必须容忍（后端扩展不视为破坏性变更）。

## 4. 响应包装与错误码

- 命令返回 `Result<T, ApiError>`；成功直接返回数据 `T`，失败返回结构化错误。
- `ApiError` 结构：

```rust
pub struct ApiError {
    pub code: String,     // 稳定错误码，如 "lan_share.peer_not_found"
    pub message: String,  // 兜底消息（开发期详细，生产可省略）
}
```

- 错误码格式：`<功能域>.<错误名>`（点分命名，全小写）。
- 错误码表必须写入对应契约文档；新增/变更错误码必须更新文档。

## 5. 国际化（i18n）约定

- 前端以错误码为 key 查本地化字典展示文案；后端不负责界面文案。
- 新增错误码时，契约文档给出中英文文案建议，前端同步写入 `locales/zh-CN.json` 与 `locales/en-US.json`。

## 6. 接口变更流程

| 变更类型 | 要求 |
| --- | --- |
| 新增命令/字段 | 追加契约文档，同步版本号（patch），无需前后端协同发布 |
| 修改语义/字段含义 | 更新契约文档，评估是否破坏性，版本号按 [versioning](../versioning.md) 递增 |
| 删除/重命名命令或字段 | **破坏性变更**：契约文档标注弃用期与迁移路径，递增 minor 及以上 |

## 7. 文档目录约定

- `docs/api/<feature>.md`：每功能一份契约文档，文件名与功能名一致。
- 契约文档的生命周期：接口实现后继续维护，直至接口废弃。
